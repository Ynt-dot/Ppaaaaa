# Архитектура

Этот документ описывает, как устроен код проекта: модели, ключевые
пользовательские сценарии и где что искать. Он ведётся вместе с кодом -
при значимых изменениях архитектуры этот файл обновляется в том же
коммите.

Для установки/деплоя см. [README.md](../README.md). Для эксплуатации
уже работающего сервера - [OPERATIONS.md](OPERATIONS.md).

## Тесты

Запуск: `python manage.py test`. Тесты лежат в `cartoons/tests/` (не
единым файлом, а пакетом из нескольких модулей по темам):

- `test_forms.py` - валидация формы регистрации (согласие с ПД,
  дубликат email, поведение при недоступности внешнего API проверки
  почты).
- `test_moderation.py` - права на удаление мульта/комментария (только
  `is_staff`, не автор/владелец), каскадное удаление вложенных ответов,
  подсчёт потомков комментария.
- `test_security.py` - валидация тегов (`_clean_tags`), регрессионный
  тест на IDOR (редактирование чужого/анонимного мульта), лимит длины
  описания, устойчивость обрезки аватара к некорректным координатам.
- `test_engagement.py` - лайки/избранное/комментарии доступны только
  авторизованным.
- `test_account_settings.py` - настройки аккаунта: смена пароля/ника/
  ссылки на профиль/описания, ЧС (блокировка/разблокировка, добавление
  по нику/ссылке/вставленному URL), запрет комментирования для
  заблокированных, модерация комментариев автором мульта, закреп
  мультов на личной странице - и что ни одно из этих действий нельзя
  подделать от имени другого пользователя (все проверки идут через
  `request.user`, не через параметр запроса).
- `test_default_avatar.py` - аватар по умолчанию: разбор ссылки на
  мульт (`_extract_cartoon_pk_from_link`), что установить его может
  только суперпользователь (обычный пользователь, `is_staff` без
  `is_superuser`, и даже прямой POST на эндпоинт в обход админки - все
  получают 403), проверка кадров у выбранного мульта, и что фолбэк на
  аватар по умолчанию не перекрывает уже выбранный пользователем свой.
- `test_avatar_link.py` - клик по аватарке ведёт на мульт-аватар, а не
  на профиль, во всех местах, где аватарка показывается (комментарии,
  блок автора на странице мульта, вкладка комментариев профиля,
  страница профиля), и откатывается на профиль, если мульт-аватар не
  выбран.

Эти тесты в первую очередь закрепляют уже найденные и исправленные
проблемы (см. "Известные ограничения" ниже) - чтобы регрессия любой из
них была замечена сразу, а не через полгода при следующем ревью.

CI (`.github/workflows/tests.yml`) прогоняет их автоматически на каждый
push в `main`/`dev` и на каждый pull request - `makemigrations --check`
(нет забытых несозданных миграций) и сам набор тестов. Запускается на
чистом окружении без `local_settings.py` (файл не в git), поэтому
`settings.py` обязан оставаться рабочим без него - это уже проверено.

## Стек

- **Backend**: Django 5.2 (LTS)
- **БД**: SQLite (разработка) / MySQL (продакшн, через ISPmanager)
- **Frontend**: серверные Django-шаблоны + ванильный JS (без SPA-фреймворка), Bootstrap 4
- **Изображения**: Pillow - сборка кадров в анимированный GIF
- **Защита от брутфорса**: django-axes
- **Хостинг**: shared-хостинг reg.ru (ISPmanager) через Phusion Passenger

## Модель данных

| Модель | Назначение |
| --- | --- |
| `Cartoon` | Сам мульт: `title`, `frames_data` (JSON-список кадров как data:URL PNG в base64), `preview` (собранный GIF), `fps`, `tags`, `description`, `views_count`, `is_pinned` (закреплён автором на своей личной странице). `author` может быть `NULL` - мульт создан анонимно (см. ограничения ниже). |
| `EmailVerificationToken` | UUID-токен подтверждения email, живёт 24 часа (`is_valid()`). |
| `CartoonLike` / `CommentLike` | Лайки, доступны только авторизованным (`user`). Уникальность лайка обеспечена `UniqueConstraint` на уровне БД. |
| `Comment` | Комментарий с вложенными ответами (`parent`, `level`), может быть закреплён автором мульта (`is_pinned`). |
| `UserPreference` | Настройки пользователя: сортировка комментариев/ленты, GIF-аватар (обрезка одного из своих же мультов), `profile_slug` (независимая от ника ссылка на профиль), `description` (профильное "О себе", до 1000 символов), `is_troll` (ставится только вручную в админке - см. "Настройки аккаунта"). |
| `UserBlock` | Запись "`blocker` заблокировал `blocked`" (чёрный список), `unique_together`. |
| `UserNote` | Приватная заметка одного пользователя о другом (видна только автору заметки). |
| `CartoonView` | Факт уникального просмотра мульта авторизованным пользователем (для счётчика уникальных просмотров). |
| `Favorite` | Избранные мульты пользователя. |
| `SiteSettings` | Синглтон (всегда `pk=1`) с общесайтовыми настройками - пока только `default_avatar_gif` (аватар по умолчанию, см. "Аватары"). |

## Ключевые сценарии

### Регистрация и подтверждение email

`register()` создаёт пользователя с `is_active=False`, отправляет письмо
со ссылкой на `EmailVerificationToken` (`utils.send_verification_email`).
Переход по ссылке (`verify_email`) активирует аккаунт и логинит.
Повторная отправка (`resend_verification`) ограничена одной попыткой в
60 секунд и завязана на `session['pending_user_id']`, а не на email из
формы - так нельзя перебором узнать, зарегистрирован ли чей-то email.

Аккаунты, которые за 24 часа так и не подтвердили почту, удаляет
management-команда `delete_unverified_users` - она не запускается сама,
её должен вызывать cron на сервере (см. OPERATIONS.md).

### Создание и редактирование мульта

`editor()` (GET/POST) принимает кадры как список data:URL PNG в base64
(рисуются в браузере, `editor.js`), собирает из них превью-GIF
(`utils.create_gif_from_frames`, максимум 50 кадров в самом превью,
максимум 5000 кадров в самой анимации) и сохраняет `Cartoon`.

Права редактирования: **строго `cartoon.author == request.user`** -
даже если мульт создан анонимно (`author=None`), отредактировать его
после этого не может уже никто, включая создателя. Раньше здесь была
дыра (см. "Известные ограничения"), сейчас закрыта.

Теги (`tags`) валидируются на сервере через `_clean_tags()`: только
список строк, максимум 20 тегов по 30 символов - и рендерятся в шаблон
редактора через `json_script`, а не напрямую в `<script>`, чтобы
пользовательский текст не мог выполниться как JS.

### Комментарии

Вложенные комментарии с ограничением на глубину инлайн-подгрузки
(`_serialize_comment`, `max_inline_level`), сортировка "по популярности"
или "по новизне" (хранится в `UserPreference.comment_sort` для
авторизованных, в сессии - для анонимов). Автор мульта может закрепить
комментарий (`pin_comment`).

Удаление комментария бывает двух видов, с разным поведением:

- **Администратор (`is_staff`)** - `delete_comment`, жёсткое удаление.
  `Comment.parent` настроен с `on_delete=models.CASCADE`, поэтому такое
  удаление рекурсивно удаляет всю ветку ответов под комментарием (на
  всех уровнях вложенности), а не только сам комментарий. Перед
  удалением фронтенд запрашивает точное число потомков
  (`get_comment_descendants_count`, тоже только для `is_staff`) и
  показывает его в диалоге подтверждения.
- **Автор комментария, или автор мульта модерирующий комментарии под
  своим же мультом** - `delete_own_comment`, мягкое удаление
  (`Comment.is_deleted`). Разрешено, если `comment.author ==
  request.user` **или** `comment.cartoon.author == request.user` -
  второе даёт автору мульта право чистить чужие комментарии под своими
  мультами обычным (не админским) удалением. Сама строка в БД не
  удаляется - иначе пропали бы ответы под ней, - только текст
  очищается и `is_deleted` ставится в `True`. `_serialize_comment` для
  такого комментария скрывает автора и текст (`author=''`,
  `author_url=None`, показывает плашку "Комментарий удалён" вместо
  текста), но лайки (`toggle_comment_like`), закрепление
  (`pin_comment`) и ответы (`add_comment` с этим комментарием как
  `parent`) продолжают работать как обычно - ни один из этих view не
  проверяет `is_deleted`. `edit_comment` на удалённый комментарий,
  наоборот, отдаёт 400. Удалённые комментарии также исключаются из
  списка "мои комментарии" в `get_user_profile_comments`
  (`is_deleted=False` в фильтре).

Аналогично у мульта два вида удаления: `delete_cartoon` (`is_staff`,
без исключений) и `delete_own_cartoon` (`cartoon.author == request.user`).
Оба жёстко удаляют запись целиком - для мультов не нужно сохранять
"ветку ответов", как у комментариев, поэтому мягкое удаление не
требуется.

### Счётчик ответов и бейдж непрочитанных

`replies_count` в `_serialize_comment` - это **все** вложенные ответы
на любой глубине (`_count_descendant_comments`, та же функция, что
считает потомков перед админским удалением), а не только прямые
дети - раньше было иначе, и число ответов под комментарием не
совпадало с реальным.

Для автора мульта (и только для него - у остальных `new_replies_count`
всегда `0`) дополнительно считается `new_replies_count`: сколько из
этих ответов созданы позже `Cartoon.author_last_seen_comments`.
Фронтенд показывает это как `2 (1) ответа`, где `(1)` - зелёным
(`repliesLabelHTML()` в `detail.html`).

Важный момент с моментом сброса `author_last_seen_comments` (тот же
таймстамп, что уже использовался для бейджа "новые комментарии" у
мульта на личной странице, `user_profile()`): раньше `detail()`
обновлял его сразу на каждый `GET` - но комментарии подгружаются
отдельными AJAX-запросами уже после рендера страницы, и к моменту их
загрузки поле было бы уже сброшено, так что бейдж непрочитанных
всегда показывал 0. Теперь `detail()` таймстамп не трогает вообще;
вместо этого фронтенд при уходе со страницы (`pagehide`) шлёт
`navigator.sendBeacon` на `mark_comments_seen` - он и сбрасывает
`author_last_seen_comments` на текущий момент. Это гарантирует, что
за время самого визита бейдж посчитан правильно (по значению "до
визита"), а после ухода - обнулится, и следующий раз на личной
странице не покажет больше непрочитанных, чем реально осталось.

### Лайки, избранное и комментарии

Требуют авторизации - `toggle_cartoon_like`, `toggle_comment_like`,
`toggle_favorite` и `add_comment` первым делом проверяют
`request.user.is_authenticated` и отдают 401/403 анониму. Уникальность
лайка дополнительно гарантирована на уровне БД (`UniqueConstraint`), а
не только в коде.

Django-сессия анонимам всё равно нужна - но только для сохранения
выбранной сортировки комментариев/ленты (`request.session`), а не для
лайков.

### Аватары

Пользователь может обрезать один из **своих же** мультов (1-10 кадров)
в круглый GIF-аватар (`set_as_avatar` + `utils.create_avatar_gif`).
Координаты обрезки, присылаемые с фронтенда, кламп(з)ятся в `[0, 1]` и
устойчивы к некорректным (нечисловым) значениям. Обрезка вынесена в
общий хелпер `_build_avatar_gif(cartoon, body)` - им же пользуется
и аватар по умолчанию ниже.

Для пользователей без своего аватара `_get_user_avatar_url()`
показывает не статичную заглушку напрямую, а сначала проверяет
общесайтовый аватар по умолчанию (`SiteSettings.default_avatar_gif`)
и только если его тоже нет - статичную картинку.

Клик по аватарке (в комментариях, в блоке автора на странице мульта,
во вкладке комментариев профиля, на самой странице профиля) ведёт не
на профиль, а на мульт, который выбран как аватар -
`_avatar_link_url(user)` отдаёт `reverse('detail', args=[pref.avatar_id])`,
если `UserPreference.avatar` установлен, и только иначе откатывается
на профиль (в том числе когда показывается общесайтовый аватар по
умолчанию - это не "мульт этого пользователя", ссылка на профиль тут
уместнее). Ссылка на профиль (username/аватарка-текст) и ссылка на
аватарку - теперь два независимых значения (`author_url` и
`avatar_link_url`/`author_avatar_link_url` в разных вьюхах), это
специально: текст с ником всегда ведёт на профиль, а кликабельна
именно картинка аватарки.

Аватар по умолчанию задаёт **только суперпользователь**, через
`/admin/cartoons/sitesettings/` - вставляет туда ссылку на **любой**
мульт любого пользователя (не обязательно свой) и после сохранения
формы попадает на страницу обрезки (`admin_default_avatar_crop`),
тот же UI, что и для обычных аватаров (`avatarCropUI` из
`base.html`). Ссылка разбирается `_extract_cartoon_pk_from_link()` -
принимает полную ссылку на мульт, путь или голый номер, для мусора
возвращает `None` и форма в админке показывает понятную ошибку вместо
падения (`SiteSettingsAdmin.response_change`). Прав суперпользователя
требуют независимо друг от друга два слоя - `SiteSettingsAdmin`
(`has_module_permission`/`has_view_permission`/`has_change_permission`
переопределены на `is_superuser`, а не только `is_staff`, как у
обычной админки) и сами view-функции `admin_default_avatar_crop` /
`set_default_avatar` (проверяют `request.user.is_superuser` заново,
без доверия к тому, что до них дошли только через админку) - так
подделать запрос напрямую на URL обрезки/сохранения не может никто,
кроме суперпользователя, даже если найдётся баг в первом слое.

### Настройки аккаунта и ЧС (чёрный список)

`account_settings` (`/settings/`, `@login_required`) - страница с
вкладками (пароль/ник и ссылка/о себе/ЧС), переключаются через
`?tab=`, как и вкладки на странице профиля. Каждая вкладка сохраняется
своим отдельным POST-эндпоинтом, и все они читают только
`request.user` - никакой из них не принимает id/username целевого
пользователя от клиента, поэтому подделать действие от чужого имени
нельзя:

- **Пароль** - `change_password`, обёртка над стандартной Django
  `PasswordChangeForm` (требует старый пароль + новый дважды),
  `update_session_auth_hash` после смены, чтобы не разлогинивало.
  Ссылка "Сбросить через почту" ведёт на уже существующий
  `password_reset` (используется на странице входа).
- **Ник и ссылка на профиль** - `update_username`. Ссылка на профиль
  (`UserPreference.profile_slug`) отделена от ника (`User.username`)
  специально: при регистрации `profile_slug` ставится равным нику
  (`register()`), но дальше живёт независимо - смена ника её не
  трогает, и её можно сменить отдельно от ника. Оба поля проверяются
  на уникальность и на допустимые символы перед сохранением. Все
  URL, ссылающиеся на профиль (`user_profile`, `_profile_url()`,
  шаблонный фильтр `profile_url`), строятся по `profile_slug`, а не по
  `username`; `_resolve_profile_user()` при поиске пользователя по
  `slug` сначала ищет по `profile_slug`, и только если не нашёл -
  по `username` (нужно только для пользователей, созданных в обход
  `register()`, например напрямую через ORM в тестах).
- **О себе** - `update_description`, до 1000 символов
  (`UserPreference.description`), отображается на странице профиля
  между блоком аватар/ник и блоком заметки.
- **ЧС** - `UserBlock(blocker, blocked)`. Добавить можно тремя
  способами: кнопка "Заблокировать" на чужой странице профиля (под
  "Количество мультов", `toggle_block_user`), серая надпись
  "заблокировать" под комментарием (тот же `toggle_block_user`), или
  вручную по нику/ссылке/вставленному URL на вкладке ЧС
  (`blocklist_add`, `_resolve_user_by_identifier` разбирает и вставленную
  ссылку на профиль, и голый ник/slug). Стафф заблокировать нельзя -
  проверяется на сервере (`target.is_staff`), кнопка блокировки для
  стаффа не рендерится вообще ни в профиле, ни в комментариях.
  Заблокированный не может оставлять комментарии под мультами того,
  кто его заблокировал (`add_comment` проверяет
  `UserBlock.objects.filter(blocker=cartoon.author, blocked=request.user)`).
  Надпись "заблокировать" под комментарием показывается автору мульта
  для чужих комментариев под своим мультом; для любого другого
  зрителя - только если у автора комментария стоит `is_troll=True`
  (`UserPreference.is_troll`, ставится вручную в админке через
  `UserPreferenceInline`, не через какой-либо пользовательский запрос).
  Уже заблокированному пользователю вместо интерактивной надписи
  показывается чёрная неактивная "пользователь заблокирован".

### Закреп мультов на личной странице

`toggle_cartoon_pin` - `Cartoon.is_pinned`, доступно только
`cartoon.author == request.user`. Работает по тому же паттерну, что и
закреп комментариев: круглая кнопка поверх превью (видна только
владельцу, `show_pin` в контексте `cartoon_card.html`), закреплённые
мульты выделены чёрной рамкой (класс `.cartoon-pinned`) и идут первыми
в сортировке альбома (`-is_pinned` первым во всех `order_by()` вкладки
"Альбом").

### Модерация администратором

`delete_cartoon` / `delete_comment` - жёстко проверяют
`request.user.is_staff` на сервере (а не только скрывают кнопку в UI),
недоступны автору/владельцу без этого флага.

### Защита от брутфорса и уведомления

`django-axes` блокирует по паре (логин, IP) после 5 неудачных попыток
на 1 час. При блокировке `signals.notify_lockout` шлёт письмо на
`ADMIN_EMAIL` и (если настроено) сообщение в Discord-вебхук - обе
переменные берутся из `local_settings.py`, вебхук опционален
(`getattr(..., None)`, ошибки отправки проглатываются, чтобы не ронять
сайт при недоступности Discord).

### Логирование

Настроено через `LOGGING` в `settings.py`: все `logger.warning()` /
`logger.error()` из кода приложения (логгер `cartoons.*`) и все 5xx/
необработанные исключения (`django.request`) пишутся в консоль и в
файл `logs/django.log` (ротация на 5 МБ, 3 бэкапа; папка `logs/`
создаётся автоматически при старте, в git не попадает).

Дополнительно, только для уровня `ERROR` и выше, есть
`cartoons.logging_handlers.DiscordLogHandler` - шлёт запись в Discord
через `DISCORD_LOG_WEBHOOK_URL` (отдельная переменная от
`DISCORD_WEBHOOK_URL`, который используется для алертов о блокировке
axes - можно указать один и тот же URL или развести по разным
каналам). Как и вебхук блокировок, эта переменная опциональна:
если не задана в `local_settings.py`, хендлер просто ничего не
отправляет (`getattr(settings, ..., None)`), а любая сетевая ошибка
при отправке в Discord проглатывается - логирование никогда не должно
быть причиной падения запроса. Обычные `WARNING` (например,
404-ответы) в Discord не летят, чтобы не заспамить канал - только
реальные ошибки.

### Согласие на куки и политика ПД

Разовый баннер про куки (флаг в `localStorage`, без серверного
хранения согласия) + отдельная страница `/privacy-policy/` +
обязательный чекбокс согласия при регистрации (`forms.py`,
`agree_to_terms`).

### Новости на главной

`index()` читает `data/news.html` (не в git, редактируется вручную на
сервере) и вставляет как есть через `|safe` - если файла нет, показывает
заглушку "Новостей пока нет". Это одно из двух мест в проекте, где
`|safe` оправдан (см. ниже "Объявление наверху заглавной"): содержимое
контролирует только тот, у кого есть доступ к файловой системе
сервера, а не рядовой пользователь сайта.

### Объявление наверху заглавной

Тем же способом, что и новости, но отдельным файлом -
`data/announcement.html` (тоже не в git; `data/announcement.html.example`
показывает формат). Файла обычно нет - тогда `index()` просто не
передаёт `announcement_content` в шаблон, и блок не рендерится вообще
(в отличие от новостей, тут нет текста-заглушки на этот случай - блок
не всегда нужен, это ожидаемое состояние, а не что-то, что нужно
объяснять посетителю). Когда файл есть, `index.html` рисует его
содержимое через `|safe` в тёплой жёлто-коричневой плашке
(`.announcement-banner` в `style.css`) над сеткой мультов. Убрать
объявление - удалить или опустошить файл на сервере, отдельного UI
для этого нет (as-is то же ручное редактирование, что и у новостей).

### Микроразметка для соцсетей

Страница мульта (`detail.html`, блок `extra_head`) отдаёт Open Graph
и Twitter Card теги: `og:title`, `og:description` (описание мульта
или сгенерированный фолбэк с названием и автором), `og:url`,
`og:image` (сам GIF-превью, если он есть) и аналоги `twitter:*`.
Абсолютные ссылки строятся через `settings.SITE_URL`, а не
`request.build_absolute_uri()` - так надёжнее за прокси/Passenger на
проде (тот же паттерн, что уже использовался для ссылок в письмах,
см. `utils.send_verification_email`) и не зависит от корректности
определения схемы (http/https) реверс-прокси. Если у мульта нет
превью - тег `og:image` просто не выводится, ошибки не будет.

### Карточка мульта (`cartoon_card.html`)

Один шаблон, два режима, переключаются флагом `compact` в контексте:

- Обычный (по умолчанию) - вертикальная Bootstrap-карточка, как в
  сетке на главной (`index.html`) и в списках на странице профиля
  (`user_profile.html`). Крупное превью, автор отдельной ссылкой,
  счётчики кадров/лайков/комментариев/просмотров.
- `compact=True` - горизонтальная строка (маленькое превью слева,
  название/автор/статистика справа, в духе списка похожих видео на
  YouTube), используется только в `get_recommendations()` для
  сайдбара "Рекомендации" на странице мульта. Вся строка - одна
  ссылка `<a>` целиком (без вложенной ссылки на автора - вложенные
  `<a>` невалидны в HTML), меньше данных в статистике (лайки/просмотры/
  время, без кадров и комментариев).

`get_recommendations()` пагинирована (`page`, 10 на страницу) так же,
как комментарии - кнопка "Загрузить ещё" под списком. `has_next`
вычисляется без отдельного `count()` на потенциально большом
аннотированном queryset: берётся `per_page + 1` записей, и если
пришла лишняя - значит, есть следующая страница.

### Подсчёт лайков и просмотров

`index()` и `get_recommendations()` считают лайки и уникальные
просмотры через коррелированные `Subquery`, а не через
`annotate(Count(...))` сразу на двух related-связях. Причина - если
в одном запросе `annotate()` два `Count()` с join к разным
related-таблицам (например, лайки и просмотры), SQL-движок перед
`GROUP BY` строит декартово произведение строк этих связей на каждый
мульт (лайки × просмотры), и запрос резко замедляется по мере роста
данных. Замерено на синтетических данных: 300 мультов × 60 лайков ×
60 просмотров - было ~7 секунд на запрос, стало ~30 мс после перехода
на подзапросы (тот же результат, без декартова произведения).
Регрессионные тесты на корректность (не на скорость - таймер в CI
нестабилен) - `cartoons/tests/test_feed.py`.

## Известные ограничения / архитектурные решения

- **Лайки/избранное/комментарии - только для авторизованных, без
  исключений.** Так было задумано изначально; ранее в моделях
  `CartoonLike`/`CommentLike` оставалось неиспользуемое поле
  `session_key` от более ранней версии (никогда не заполнялось,
  поскольку создание лайка возможно только после проверки
  `is_authenticated`) - убрано вместе со связанными фильтрами и
  прокидыванием `session_key`/`_ensure_session` через
  `_serialize_comment` и все read-эндпоинты комментариев.
- **Анонимные мульты неизменяемы после создания.** Раньше `editor()`
  проверял права только когда у мульта был автор, из-за чего мульты без
  автора мог редактировать кто угодно (IDOR) - вместе с отсутствием
  валидации тегов это давало stored XSS. Сейчас доступ закрыт полностью;
  если понадобится "дорисовать" анонимный мульт после логина - этот
  функционал придётся проектировать отдельно (например, привязку через
  токен в сессии в момент создания), а не ослаблять текущую проверку.
- **`DEBUG` по умолчанию `False`** в `settings.py` - если
  `local_settings.py` вдруг не переопределит его, сайт не откроет
  подробности ошибок публично.
- **`django-debug-toolbar` подключается только при `DEBUG=True`**
  (и в `INSTALLED_APPS`/`MIDDLEWARE`, и в `requirements-prod.txt` его
  вообще нет) - на проде этого пакета физически нет в окружении.
- **Выход из аккаунта - только через `POST`.** Встроенный `LogoutView`
  Django перестал принимать `GET` (устарело в 4.1, убрано в 5.x) - при
  апгрейде на Django 5.2 ссылка `<a href="{% url 'logout' %}">` в
  `base.html` превратилась в 405. Заменена на `<form method="post">` с
  `{% csrf_token %}`. Регрессионный тест -
  `cartoons/tests/test_logout.py`.
- Список запланированных фич и известных небольших багов - в README,
  раздел "ЗАДАЧИ" (не дублируется здесь, чтобы не расходиться).
