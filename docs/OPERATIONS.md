# Эксплуатация (runbook)

Этот файл - не замена README. Установка и обновление сервера подробно
описаны в [README.md](../README.md) ("Установка на продакшн",
"Обновление продакшена"). Здесь - то, чего в README нет: как
диагностировать проблемы на уже работающем сервере, разовые
настройки (cron) и типовые операции вроде сброса пароля.

Все пути ниже используют плейсхолдеры в духе `local_settings.py.example`
(`<username>` вместо реального логина хостинга) - подставляйте свои
реальные значения по месту, но не публикуйте их в этом файле, репозиторий
публичный.

## Окружения

| Параметр | Разработка | Продакшн |
| --- | --- | --- |
| ОС | Windows | Linux (reg.ru, ISPmanager) |
| БД | SQLite | MySQL |
| `DEBUG` | `True` | `False` |
| Веб-сервер | `manage.py runserver` | Phusion Passenger (`passenger_wsgi.py`) |
| venv | `venv/` | `~/djangoenv` (имя может отличаться - проверьте `ls ~`) |

Оба окружения настраиваются через `Ppaaaaa/local_settings.py` (не в
git). Актуальный список нужных ключей и их смысл - в
`Ppaaaaa/local_settings.py.example`. Коротко, зачем нужен каждый
неочевидный ключ:

- `ADMIN_EMAIL` - куда падает письмо о блокировке пользователя/IP (см. `cartoons/signals.py`).
- `DISCORD_WEBHOOK_URL` / `DISCORD_ADMIN_USER_ID` - опциональное дублирование того же уведомления в Discord. Если не заданы - просто не используются, ошибок не будет.
- `SITE_URL` - базовый URL для ссылок в письмах (подтверждение email).

## Cron-задачи

### Удаление неподтверждённых аккаунтов

Аккаунты, не подтвердившие email за 24 часа, сами себя не удаляют -
нужна задача в **ISPmanager -> Cron-задачи** (или Планировщик CRON):

```bash
cd /var/www/<username>/data/www/<домен> && source /var/www/<username>/data/djangoenv/bin/activate && python manage.py delete_unverified_users >> /var/www/<username>/data/logs/cron.log 2>&1
```

Расписание - раз в сутки достаточно (задержка в 24 часа не требует
частого опроса). Проверить, что задача реально отрабатывает:

```bash
cat /var/www/<username>/data/logs/cron.log
```

Там должны появляться строки вида "Удалено N неактивированных
аккаунтов." или "Нет аккаунтов для удаления." после каждого запуска.

## Частые операции

### Забыли пароль администратора (суперпользователя)

Не нужно вспоминать старый пароль - можно назначить новый напрямую:

```bash
python manage.py changepassword <username_админа>
```

Если неизвестно, кто вообще суперпользователь:

```bash
python manage.py shell -c "from django.contrib.auth.models import User; [print(u.username, u.is_superuser) for u in User.objects.filter(is_superuser=True)]"
```

Суперпользователей вообще нет - создайте нового: `python manage.py createsuperuser`.

### Кто-то заблокирован django-axes раньше времени / нужно снять блокировку

```bash
python manage.py axes_reset            # снять все блокировки
python manage.py axes_reset_username <username>
python manage.py axes_reset_ip <ip>
```

### Проверить, что сайт не работает с `DEBUG=True` на проде

```bash
python manage.py shell -c "from django.conf import settings; print(settings.DEBUG)"
```

Должно быть `False`. Если `True` - смотрите `Ppaaaaa/local_settings.py`
на сервере, там должно быть `DEBUG = False`.

## Логи и диагностика

- Cron-логи: `/var/www/<username>/data/logs/cron.log` (или другой путь,
  указанный при создании задачи в ISPmanager).
- Ошибки Passenger (500-е на сайте, не связанные с самим кодом
  представления) - смотрите логи приложения через ISPmanager
  ("Сайты" -> домен -> "Логи") либо стандартный `passenger.log`, если
  доступен через SSH.
- Диагностика конкретной 500-й ошибки Django - временно посмотреть
  `DEBUG=True` **только локально на копии базы**, не на проде (см.
  предупреждение ниже).

## Предупреждения

- **Никогда не включайте `DEBUG=True` на проде**, даже временно для
  диагностики - страница ошибки Django с `DEBUG=True` показывает всем
  посетителям полный traceback вместе с содержимым `settings.py`,
  включая `SECRET_KEY`, пароль от почты и токен Discord-вебхука.
  Для диагностики воспроизводите проблему локально или временно снижайте
  уровень логирования вместо включения `DEBUG`.
- **Перед миграциями на проде и перед мажорными обновлениями
  (например, апгрейд Django)** сделайте бэкап БД (`mysqldump`) - на
  shared-хостинге откатить миграцию руками сложнее, чем восстановить
  бэкап.
- `git pull` на сервере может конфликтовать с локальными правками
  (например, если `passenger_wsgi.py` редактировали прямо на сервере) -
  см. раздел "Обновление продакшена" в README для типового решения.
